# Prompt Studio

A local tool for improving the default AI prompts of every workflow stage. You edit each
prompt as numbered sections, test a change with several independent agents, keep score, and
build the seed file that installs the prompts.

Working with it is local: its commands only read and write files in this folder. They never
create branches, commits or pull requests. Git sees your edits like any other file change;
commit and push them when you choose. Undo is built in (`revert`, `restore`). The tool is
not deployed.

## Run it

From the repository root, with the backend environment (it renders prompts with the app's
own renderer). A shortcut for your terminal:

```bash
alias studio="web_app/backend/.venv/bin/python web_app/prompt_studio/studio.py"
```

Then open `web_app/prompt_studio/out/studio.html` in a browser (on a Mac: `open` it). The
page is view only; refresh it after each `build`.

## Files

| Path | What it is |
| --- | --- |
| `prompts/<stage>.md` | One file per stage: its system prompt and instruction prompt, with numbered headings |
| `prompts/<stage>.md.previous` | The version `revert` or `restore` last replaced (one-step undo) |
| `prompts/_imported.json` | Fingerprints of the seed at the last import; `status` uses them |
| `fixtures/<stage>/<name>.json` | Made-up test inputs and the answers they should produce |
| `evals/<stage>.md` | The scoreboard: one scored table per test, newest last |
| `evals/<stage>/<label>/` | One test: its packets, the agents' results, and the exact prompts it tested |
| `out/` | Generated by `build`: `studio.html` and the seed file. Safe to delete |
| `studio.py`, `page.html` | The tool and its page template (tests: `tests/web_backend/test_prompt_studio.py`) |

`out/`, the test folders `evals/<stage>/<label>/` and the `*.previous` undo files are local
working files and stay out of git (`.gitignore`). Everything else here is committed.

A stage id is `workflow.mode.stage`, with `common` when a stage has no mode, for example
`analysis.one_shot.per_table_authoring`. There are 19 stages.

## Stage files and section numbers

```text
<!-- Prompt Studio stage analysis.one_shot.per_table_authoring. ... -->
<!-- agent_tool_names: null -->

<!-- ===== SYSTEM PROMPT ===== -->
## [S1] Role and outcome
...
## [S8] Hard cases
### [S8.1] ...
<!-- ===== INSTRUCTION PROMPT ===== -->
<key_directory>
{{ key_directory }}
</key_directory>
## [I1] Task
...
<!-- ===== END ===== -->
```

- `[S3]` is the third `##` heading of the system prompt, `[S3.2]` the second `###` inside it,
  and `[I1]` the first `##` heading of the instruction prompt. Refer to sections by these
  numbers: "rewrite S6", "merge S7 into S6", "add a rule to I1".
- The numbers exist only in studio files. `build` removes them, so the model never sees them,
  and renumbers the file after headings are added, removed or moved. Never renumber by hand.
- Keep the four `<!-- ===== ... ===== -->` marker lines. Change the `agent_tool_names` line
  only to change a tool stage's tools (`null` means all registered tools).
- `{{ name }}` inserts a variable. Only the stage's registered variables are allowed; the
  page lists them with their structure and an example. Values arrive as compact JSON with
  sorted keys. Templates use restricted Jinja (`{% if %}`, `{% for %}`, `tojson`).

## Commands

| Command | What it does |
| --- | --- |
| `status` | For each stage: `in sync`, `edited in studio`, `seed changed` or `both changed` |
| `import [--force]` | Copy every seed prompt into `prompts/`. Refuses to overwrite studio edits unless `--force` |
| `build` | Renumber, check every stage (it must render with the registered examples and stay within size limits), write `out/studio.html` and `out/05_global_prompt_defaults.template.sql`. Exits 1 on any `PROBLEM` |
| `revert <stage>` | Put one stage back to the seed's prompt |
| `restore <stage> <label>` | Put back the prompt version that test `<label>` measured |
| `fixture <stage> <name>` | Create a starter test input from the registered example values |
| `pack <stage> <fixture> [--runs 3] [--label name]` | Write blind test packets: the seed prompt (baseline) and your edited prompt (candidate), `--runs` of each, shuffled |
| `score <stage> <label>` | Score the returned results, print the table and add it to the scoreboard |

## The loop

1. `studio status`. Start in sync; if the seed changed, run `studio import` first.
2. Edit `prompts/<stage>.md`, or ask an agent: "In `analysis.one_shot.per_table_authoring`,
   rewrite S6 so that ...".
3. `studio build`, then refresh the page. Changed sections are marked, with a diff against the
   seed.
4. Test the change (next section) and read the score.
5. Decide:
   - Better: keep it.
   - Worse: edit again, `studio revert <stage>` to drop it, or `studio restore <stage> <label>`
     to go back to an earlier tested version.
6. When a version is good and the user asks: `studio build`, copy
   `out/05_global_prompt_defaults.template.sql` to `database/seed/`, run `studio status` (now
   `in sync`) and run the checks at the end of this file.

## Testing a change and keeping score

A change moves through: edited → packed → run by agents → scored → kept or reverted.

1. Pick a fixture for the stage in `fixtures/<stage>/`, or create one (see Fixtures).
2. `studio pack <stage> <fixture> --label <short-name>`. You get 3 baseline and 3 candidate
   packets in `evals/<stage>/<label>/`; their names do not say which is which. If the stage
   has no studio change, every packet is the baseline (useful as a reference score).
3. Run each packet in its own fresh agent, giving it only this message:
   `Read <packet path> and follow it exactly.`
   The agent answers as the model, reviews the prompt, and writes `<run>.result.json` next to
   the packet.
   - Claude Code: one sub-agent per packet, in parallel. Or just ask: "run the `<label>` packets".
   - Codex, Copilot or any other agent: one new chat per packet with that single message.
   - Use the same model for every run, ideally one close to the production model. Give the
     agent no other context and never say which variant it has.
4. `studio score <stage> <label>`. The table is printed, added to the scoreboard
   `evals/<stage>.md`, and shown under Tests on the page.

| Score | Meaning |
| --- | --- |
| Valid answers | Answers that match the stage's output schema |
| Expected items found | The fixture's expected items present in valid answers. Higher is better |
| Forbidden items returned | Items the fixture says must not appear. Lower is better |
| Other items | Items the fixture does not mention. Read them; they may be fine |
| Clarity, Confidence | The agents' 1–5 ratings |
| Blockers cited | Sections that made agents leave out something they believed was right |
| Confusing cited | Sections agents found unclear or conflicting |

The suggested verdict is `better` when expected items found rise by 10 points or more with no
more forbidden items or invalid answers, `worse` when either gets worse, and otherwise
`same`. It is a suggestion: read the review notes too. Test a change on more than one
fixture, with at least 3 runs each; a one-run difference is noise. The test agents are not
the production model, so confirm a kept change with a real Run.

## Fixtures

```text
{
  "description": "One sentence: what situation this input tests.",
  "values": {"<variable name>": <value>, ...},
  "output_schema": {...},                      the stage's required_output_schema
  "expect": {
    "list": "relationships",                   dot path to the list of answer items
    "key": ["from_attribute_name", "to"],      fields that identify one item
    "expected": [{"from_attribute_name": "employeeid", "to": "t1.employeeid"}],
    "forbidden": [{"from_attribute_name": "employeeid", "to": "t4.employeeid"}]
  }
}
```

- Use made-up data only. Never paste real tenant metadata, prompts from Runs or physical rows.
- `values` must match each variable's structure; `build` and `pack` check them.
- `fixture` fills `output_schema` for the Analysis stages. For other stages, copy the stage
  validator's `output_schema()` from the backend.
- Only `one_shot` stages can be tested: tool stages need live tool results.

## Keeping the seed in sync

- The seed file is what installs; the studio files are where you edit.
- Run `studio status` before starting work and after copying the seed.
- Only v1 (`database/seed/05_global_prompt_defaults.template.sql`) is managed. While the v2
  file exists, the per-table Analysis prompt must be identical in both seed files: copy a
  changed per-table prompt into v2 as well.

## Checks

The tool's own tests (they also run with the normal backend tests):

```bash
PYTHONPATH=mcp_server:web_app/backend:. web_app/backend/.venv/bin/python -m pytest -c web_app/backend/pyproject.toml tests/web_backend/test_prompt_studio.py -q
```

After copying a new seed into `database/seed/`, also run the prompt tests:

```bash
PYTHONPATH=mcp_server:web_app/backend:. web_app/backend/.venv/bin/python -m pytest -c web_app/backend/pyproject.toml tests/web_backend/test_logical_prompt_guidance.py tests/atlas/test_shared_modeling_rules.py tests/mcp/test_database_global_prompt_seed.py -q
```

The last test file needs Docker for its disposable database.

## Rules for agents working here

- Work locally: edit the files directly. Never create branches, commits or pull requests while
  working here; the user commits and pushes. Undo with `revert` and `restore`, not git.
- Edit only `prompts/` and `fixtures/`; `pack` and `score` write `evals/`. Never edit `out/`.
- Point at and change prompt text by section number.
- After editing, run `build` and fix every `PROBLEM` line.
- Do not copy the built seed into `database/seed/` unless the user asks.
